## 1. 判断：先提高核查可靠性，再检验价值维度的额外作用

建议把 verifier 改为“query 必要条件 → 帧证据 → 条件判断 → 边界核查 → 可追溯结论”。五类价值作为提出核查问题的辅助视角，是否有用通过对照验证；不把精彩程度作为 grounding 正确性的门槛。

不宜仅把价值提示写长，再观察 NA 是否变少。当前结果同时存在引用失效、时间关系错误、query 条件漏查；价值字段本来就不直接参与最终报警。更多非空字段不等于更多正确反例。

## 2. 改进一：逐项核查 query，避免“识别到名词就通过”

把请求中的必要条件整理为可核查项，保留原文范围和 AND/OR、否定、时间先后关系，避免重演旧 TaskSpec 给通用请求添加 object 约束的问题。条件只能来自用户 query 的要求；不能自动添加成功、庆祝、情绪强烈等要求。普通多条件请求可按主体、动作、对象、关系与结果组织，不强制所有 query 填齐所有类别。

例如 qid 9572 的“男子查看横屏手机上的文章”，需要分别验证人物与手机的关系、横屏、内容是否为文章。“有手机”不能替代“内容为文章”。旧输出同时给出 query=supported 和“是否为文章尚待确认”，说明现有整体判断遗漏了必要条件。

每个条件保留支持、反证或证据不足及来源。对合取条件，关键项仍 unknown 时不得将整体写成 supported；OR 等条件按原请求逻辑处理。缺少采样证据不等于 contradicted。建议将缺证问题绑定到具体条件 ID，避免一段未绑定的 `missing_evidence` 与 supported 互不约束。

这是拟议结构调整，尚未实现。条件拆解也可能漏条件或引入条件，因此它必须先独立审查，不能把模型生成的 checklist 当作天然正确的 TaskSpec。

## 3. 改进二：将边界方向与可检查的证据关系绑定

让模型回答“哪里出现了什么、是否属于同一次目标事件”，由程序读取冻结 PTS/region 检查方向；不要依赖模型在理由中重新心算帧属于片前还是片后。

| 要判断的问题 | 最低证据要求 | 对应边界意见 |
|---|---|---|
| 开头包含不属于目标事件的内容 | 片内开头的无关内容及目标事件锚点 | start too_early |
| 同一次目标事件在起点前已开始 | before + inside，且同次事件关联成立 | start too_late |
| 同一次目标事件在终点后继续 | inside + after，且同次事件关联成立 | end too_early |
| 结尾包含不属于目标事件的内容 | 片内结尾的无关内容及目标事件锚点 | end too_late |

例如 qid 9394 的理由是事件在结束后仍继续，却输出 end=too_late；如果同次事件的继续确实成立，应对应结束过早。qid 9572 又把 35.235–36.737 秒说成 37 秒之后，实际 PTS 查表可以阻止这种位置错误。

CPU 只能核对位置、引用和条件组合，不能证明画面真的无关或属于同一次事件。不能仅因看到 before/after 内容就自动报警；自然转场、重复事件、标注采用更长叙事范围都需保留不确定性。稀疏帧也不足以证明精确边界，暂不生成修订时间戳。

## 4. 改进三：价值维度改为目的相关的核查提示

建议把“这个片段有什么价值”具体化为“该价值视角能帮助核查 query 的哪个必要条件”。

| 维度 | 有用的核查问题 | 不应自动附加的要求 |
|---|---|---|
| outcome | query 要求的完成结果是否出现，例如进球还是射门尝试？ | 每个动作都必须成功 |
| information | 内容/界面细节是否足以确认 query，例如文章还是视频？ | 描述越丰富，片段越正确 |
| emotion | query 要求的情绪是否可见，是否归属于目标人物/事件？ | 普通动作也必须激动 |
| action | 必需动作、关系或阶段是否发生，而非仅物体出现？ | 必须补全任意前奏与庆祝 |
| sensory | query 指定的颜色、方向、外观等是否可辨？ | 画面必须漂亮或具有冲击力 |

状态定义应明确：**NA 是任务不需要；unknown 是任务需要但当前证据不足；supported/contradicted 才是有来源的肯定/反证。** 不应把“已看见并匹配”或“暂时看不清”当作 NA 的理由。

qid 5466 需要确认剪辑软件是否展示视频制作过程，仅确认软件存在不足以回答；qid 4008 的餐盘图像不足以确认是谁在介绍早餐，应保留相关条件未知。普通“男子说话”则可以正确地令 emotion=NA。

研究上必须承认：这里部分价值提示可能只是普通 query 语义核查的另一种表述。如果没有比 query-only 核查带来额外收益，就不应把五维模块包装成已证明有效的贡献。

## 5. 技术修复单独处理，不用修写旧输出代替验证

- 原 query、帧 ID、PTS、区域由程序提供/查表，尽量避免让模型重复抄写；query 引文的空格/拼写问题与语义条件遗漏分别记账。
- 减少输出里反复转述相同时间/区域信息的负担，评估更直接的证据绑定结构；保留事实文字与图像来源的可追溯关系。
- 无引用、引用不存在或跨区域不合规时，不能自动补齐事实、静默去重或转为合法支持。原 58 个失败完整保留。
- 如果调整引用表示、schema 或控制器，应单列新版本，并承认是工程组合变化；不能把与旧 v1.1 的差异归因于价值提示这一单变量。

这些是待实现建议。本轮没有修改契约或运行器，没有为旧预测生成“修复后成绩”。

## 6. 建议的最小验证顺序

### P0：先明确人工审阅标准和 CPU 契约

复用已有 12 条固定案例作为开发回归案例，检查四种边界方向、NA/unknown、漏必要条件及引用异常。不得把它们重新包装为独立测试集。通过现有查看页面组织后续独立人工审阅，至少区分：明确错事件、必要条件无法证实、边界/覆盖问题、可能标注口径差异、无法判断；标注问题单列待核，不从分母删除。当前独立人工审阅人数/条数仍为 0。

### P1：建立可解释的 query-only 核查版本

先实现条件核查和证据绑定/边界控制；固定 base、原 query、同一旧帧像素/PTS、模型及评价。新版本与 v1.1 的比较是组合修订评估，不声称单一因果。确认引用可靠性、方向一致性和缺证处理后，再问价值提示是否有增益；不直接接入记忆、回看或区间修正。

### P2：冻结公共实现，做 Q 与 Q+V 配对对照

- **Q**：query 条件、证据和边界核查。
- **Q+V**：沿用 Q 的输入、条件定义、公共输出契约和报警规则，只增加五类价值的核查提示；不另加精彩度阈值。尽量不增加独立长篇输出，避免同时比较两套 schema。
- 唯一拟干预是价值核查提示；提示长度及由此造成的注意力变化不可完全消除，须披露，不能称为纯粹“价值理解”因果证明。
- 建议先取原清单中按原顺序固定的 20 个 query，纳入各 query 的全部候选，包括无候选项的总体记账。清单和候选数需在新预测/评价前冻结，不按 IoU、旧模型成败或案例印象挑选，也不替换失败项。实际每臂请求数是候选数 N，不能把 20 个 query 当成 20 次请求。
- 这仍是已反复审查过的 train 开发池，只能做机制筛选；独立泛化结论需后续未用于调整提示的样本。

**主要看**：引用合法率、必要条件判断是否有证据、边界理由/方向一致性、误报、反例召回及 unknown 的合理性。沿用 IoU 错误代理，并将人工语义判断分列。不要把非 NA 比例、理由更长或报警更多当成主要成功指标。

保留全部候选失败分母，报告两臂配对变化和按 source video 聚类的不确定性；小样本不能宣称显著提升。不改旧 CPU 时长阈值。原正式探索门槛（138/139 合法、precision≥80%、recall≥30%、正确区间误报≤10%、insufficient≤40%、至少20个flag）继续作为原139候选协议的门槛，不能用20-query机制小试宣称已通过。

如果只改善合法率而语义误报不改善，停止扩大，继续定位内容错误；如果价值字段更多但筛查没有收益，保留 query-only 作为更简方案。若主要瓶颈确认为旧帧看不到必要细节，再单独研究针对缺失条件的回看，而不是现在同时加入采样、ROI、记忆和模型更换。
