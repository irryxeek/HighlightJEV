## 1. 修订后的目标与范围

首版验证：**用同一个 VideoJev-4B、同一份全片视觉输入，能否通过窗口评分、事件合并复评、同类候选比较，形成可用的高光区间和预算选片结果。** 排序服务于选片与定位；粗区间可运行不等于精细 grounding 已解决。

```text
固定全片采样帧＋真实 PTS → 官方 Cached 视频前缀
    L1：等长窗口 × 五维价值 ×（0–5＋未知）
    L2：候选覆盖 → 邻接合并判断 → 合并区间重新评分
    L3：有限候选的同类比较 → 局部调整顺序
    程序：去重、时长预算选择、区间与分数导出
```

模型只回答选择题并返回选项概率。程序保存时间、概率、父子区间、排序变化与成本，无需生成 caption、事实列表、证据链、理由或计划。

首版不加入工具调度、动态记忆、源视频回看、新增音频/ASR/OCR、±2/4/6 秒边界搜索、在线流式判断或训练。原稿中这些内容作为未来扩展保留，不删除历史设计与实验记录。[完整扩展方案](highlightjev_agent_framework_plan_2026-11-12.md)和[v5 图稿](../projects/videojev_agent_framework_20261112_v5/README.md)仍可阅读，但不代表本版实现范围。

## 3. 模型、缓存与输入约定

选用 **MCG-NJU / ZhuYuhan VideoJev-4B**，复用官方原生 Cached 路径。官方多选 QA 直接评估选项，返回概率、答案索引和选项文本；我们把七档评分和合并、比较问题组织为选择题，不新增未经训练的评分头。[官方 README](https://github.com/MCG-NJU/VideoJev/blob/7f8b38aa7df67721303cdc61f06d8435f3c7db89/README.md)、[选择题输入代码](https://github.com/MCG-NJU/VideoJev/blob/7f8b38aa7df67721303cdc61f06d8435f3c7db89/timejev/decision_inputs.py)

缓存是全片输入的模型前缀状态，不是生成的背景文字或语义记忆库。各题从同一前缀独立读取，不能把前题答案累积到后题；每题仍有后缀计算成本。具体 4B 权重、执行器及跨问题隔离尚需联调，不能以接口存在代替实测。[缓存实现](https://github.com/MCG-NJU/VideoJev/blob/7f8b38aa7df67721303cdc61f06d8435f3c7db89/timejev/asymmetric_video_memory.py)

当前公开用法说明 QA 使用视频帧，不包含音频或字幕输入。本版按视觉方案实施；采访内容、不可见声音等信息不足时允许未知，不靠生成理由补足。[官方用法](https://huggingface.co/ZhuYuhan/VideoJev-4B/blob/main/USAGE.md)

对照条件固定同一模型、像素/真实 PTS、全片上下文、评分语义和导出规则。L2/L3 只是换目标区间与问题，不新增采样或局部裁剪。全片输入是**固定采样的全时段覆盖**，不表示读取每一帧；超过容量须先明确分段方案，不能运行中静默截断。

TVSum 首轮使用固定的通用高光目标，不把“精彩时刻”误提取成物体约束，也不额外加入 Query 解析或相关性调用。将来处理具体用户请求时，再把任务条件作为独立设计变量。

TVSum 建议先沿用旧 3 秒目标窗口及末尾处理规则。旧流程以 2fps 读局部帧、导出 2 秒评价分数；新 JEV 的全片帧池、帧数上限、预处理和视觉 token 预算须另行冻结。跨模型对照不声称处理后的视觉 token 完全相同。[旧 val10 协议](revalue_generic_highlight_tvsum_val10_protocol_2026-11-10.md)、[全50协议](revalue_generic_highlight_tvsum_full50_8b27b_protocol_2026-11-10.md)

## 4. L1：全时间轴的五维评分

### 4.1 评分对象与具体锚点

每个窗口分别询问五个维度对“保留这个片段作为本视频高光”的贡献。**是否相关、属性是否存在、物理强度、观看贡献是不同概念**；这一区分体现在问题和选项里，不要求为四个概念分别调用模型。

下面是拟实现的语义锚点，运行前需冻结最终问题全文与英文选项。五维存在交叉，不能视为独立、已校准的心理量表。

| 维度 | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 结果 Outcome | 无新增事件进展或结果贡献 | 重复准备、仅建立背景 | 可辨认的局部推进 | 影响后续的关键步骤 | 重要结果或明显转折 | 决定主事件走向的结果/转折 |
| 信息 Information | 无新增有效信息；仅品牌/身份展示不自动加分 | 少量辅助细节 | 有用但非关键的新细节 | 对理解过程必要的说明或对比 | 明显改变对事件的理解 | 揭示主问题的关键答案或核心变化 |
| 情绪 Affect | 没有额外情绪观看贡献 | 礼貌微笑、常规反应 | 清楚但普通的事件相关反应 | 持续且有意义的明确反应 | 强烈且归属清楚的关键反应 | 构成主事件情绪高潮的反应 |
| 动作 Kinetic | 普通位移/重复动作无新增贡献 | 常规执行或准备 | 有辨识度的技术环节 | 关键动作或明显执行差异 | 突出的难度、完成度或动作高潮 | 决定该事件价值的核心动作片刻 |
| 感官 Sensory | 普通清晰画面，无额外贡献 | 一般装饰性变化 | 值得注意的具体视觉细节 | 与事件有关的突出呈现 | 少见且对观看有明显贡献的变化 | 视觉呈现本身构成该事件不可替代的核心 |

`U（未知）`：当前采样不足以判断该维贡献，或判断依赖未提供的模态。它既不是 0，也不是低强度。0 表示该维未提供额外高光贡献，并不证明某物体、动作或情绪不存在。

有重要影响的失败也可得到高 Outcome；尝试动作不等于成功，但“失败”不能自动判低价值。大声、人数多、危险或鲜艳都不是高分的充分条件；情绪和感官分级仍需与当前事件的贡献相联系。单维突出可以入选，不要求五项全高。

这些约束承接了既有品牌/主体展示抢占前列、普通微笑被放大、关键行走/动作片段被漏选等现象；它们是设计动机，尚不能证明新规则有效。[8B 低 AP 诊断](revalue_generic_highlight_tvsum_8b_improvement_diagnosis_2026-11-10.md)

### 4.2 输入、概率与未知

每题明确 `video_id`、目标 `[start,end)` 与维度，问题只要求对目标区间评分；全片帧用于背景，不允许把别处发生的高潮记到目标窗口。示意：

```text
Use the fixed video context to assess [start, end).
How much does this interval contribute to the video's highlights
through [dimension]? Select the best-fitting contribution level.
Judge this interval independently; equal scores are allowed.
Options: six dimension-specific descriptions for 0–5; U = cannot judge.
```

保存 `p0…p5,pU`。对可判断维度，使用已知等级条件期望作为**待验证读出**：

`s_d = (0*p0 + 1*p1 + ... + 5*p5) / (p0 + ... + p5)`。

首版可采用“U 为最大概率选项（含并列）则该维置未知”的简单规则；如另加未知概率门槛，须在运行前冻结。不能丢掉 `pU` 后把条件期望冒充可靠度，也不能把序数期望称为已校准的高光概率。

融合建议先取最强有效维度 `s = max(s_d)`，不同时搜索多套权重。它保留单维高光，也会放大误判，必须验证。全维未知保留 `null`；全网格导出时如何处理未知与技术失败须独立冻结，保留完整分母，不能删掉困难窗口或解释为模型判定非高光。

## 5. L2：候选覆盖、合并与独立复评

L1 评分覆盖全片，进入 L2 的问题数量有限。候选采用**每维 Top-K 的并集＋固定时间覆盖名额**，未知窗口另按预定规则保留少量名额。确定总数上限、去重、同分顺序和名额冲突处理；不读取 GT，也不按已有 AP 挑视频。实际 K 与配额在输入清单和成本估计后冻结，不把召回限制为总分 Top-5。

对预先生成的时间邻接候选，只问：

> A 与 B 是否为同一连续事件/过程，适合合成一个高光候选？

选项为“合并／不合并／无法判断”。仅时间相近、高分相近或主体相同不足以合并；同一动作的回放与新发生的一次动作也要区别。未知时保留原候选。程序限定邻接范围、允许间隙、合并方向、最大时长，避免连续局部肯定无上限地串成长事件。

合并后使用父窗口外包络，给新候选分配程序 ID，**重新询问五维贡献，不累加子窗分数**。不把 L1 分数、名次或所谓理由放进复评提示。未改变的单窗口复用 L1 结果，避免重复调用；所有子窗口保留，供预算适配和错误追踪使用。

本层产物是“事件候选”，不是经过核实的完整事件图。不会寻找新的边界帧；只凭当前固定帧无法确认完整动作时，应保留未知而不是宣称边界准确。

## 6. L3：有限的同类候选比较

目的：处理已有候选中“同一标准下哪个更值得保留”的细微差异。五维分布只用于预筛共同标准，不能证明两段属于同类事件。

比较问题给出 A/B 时间范围和共同价值标准，隐藏此前数值与排名，选择：

`A 更值得保留 / B 更值得保留 / 贡献相当 / 不适合比较 / 无法判断`。

候选标识不编码名次；两向问题从相同视频前缀独立执行，B/A 不读取 A/B 的答案。时间位置本身保留，用来绑定目标区间。

“相当”表示能够比较但差异不足；“不适合比较”表示缺乏共同标准；“无法判断”表示当前输入不足。首版不另做复杂资格验证，也不把后两项当成并列或强迫胜负。

建议最小改序实现：从 L2 原顺序一次性生成**固定、不重叠的相邻候选对**，仅对有共同比较标准且影响预算选择的前部候选进行有限复核；每对询问 A/B、B/A 两个方向。两向同意同一赢家才允许交换；冲突、相当、不可比、未知均保留 L2 顺序。配对后不自适应追加新的问题，也不做全候选两两比较。

这是可解释的局部改序基线，不等于求得全局最优排名。同维内比较也不能直接推导跨维的统一胜率；不同选项集合的 softmax 概率不作为可跨集合相加的“价值”。固定配对规则、先后顺序和问题上限须随协议保存。

## 7. 预算输出与最少记录

输出程序按最终顺序选择候选，去除重复覆盖，再按时间顺序呈现，满足 `总播放时长 ≤ B`，不必凑满 B。若事件超过剩余预算，可依预定规则使用保留的较短子窗或跳过；不任意截断动作、不声称做了边界优化。重叠区间如何合并、去重后怎样计时，需由同一个确定性适配器处理。

只保存程序可直接获得的内容：输入与模型版本、帧/PTS 哈希、问题与选项版本、完整概率和未知、父子窗口 ID、比较双向输出、改序前后列表、最终区间、错误及实际成本。无需生成 `evidence_ids`、事件理由或事实/决策记忆。

**稠密分数与事件清单分别保存。** L1 可按真实时间重叠映射为既有评价网格；L2/L3 若要报告同口径 mAP，必须先固定合并覆盖冲突、事件分数投影和改序导出规则。不能只对留下的候选算 mAP，不能在看到 GT 后决定映射。尚未完成该适配时，只报告相应候选/预算输出，不编造全视频指标。

## 8. 对照设计与推进顺序

| 问题 | 最小对照 | 可以回答什么 |
|---|---|---|
| 五维规则是否有用 | 同 JEV 通用高光单题 G0 vs 五维 L1 | 在相同视觉输入下的规则效果；问题数量不同，必须同时报告成本 |
| 合并复评是否有用 | L1 vs L1＋L2 | 合并与事件级重评分整体是否改善候选/选片；不单独归因为事件身份判断 |
| 相对比较是否有用 | L1＋L2 vs L1＋L2＋L3 | 固定比较规则的改序、弃判、输出和成本变化 |
| 与既有方法相比如何 | 相同视频上的 REZE 结果作为外部参照 | 系统效果差异；骨干、上下文和输入处理不同，不能归因于单个模块 |

推进按以下顺序，避免一开始铺开全部条件：

1. **CPU 准备**：实现选择题适配、时间索引、概率校验、未知处理、候选/合并/比较规则与预算输出；用构造输入检查契约，完成源码和配置冻结。
2. **最小功能验证**：获得独立运行授权后，验证官方 Cached 与 4B、实际上下文容量和题目隔离，再打通 L1 的完整曲线和预算输出。技术失败先定位，不自动扩样。
3. **固定小规模 L1 对照**：优先沿用已有 TVSum 开发清单，完整报告所有视频。标明已经多轮观察过该清单；不能称独立测试集，也不能据此定论泛化。
4. **逐层增加**：L1 输出有效后，固定同一输入分别加 L2、L3；候选和派生问题由已冻结规则产生。保存每层产物，分别报告功能与科学结果。

TVSum 可沿用已有 Top-5/15/50 mAP 评价口径，但各条件必须有相同完整评价网格和冻结导出规则；配对区间以视频为单位。候选召回、选片冗余和时长违约另报。定位/边界收益应在有相应时间标注的任务上检验，不能由 TVSum 排序结果代替。

时间内全同分、全未知、L3 全相当、零改序都可以是有效负结果，原样保存；技术运行成功不代表门槛已通过。归纳模型结论前须先排除输入/时间错配、缓存污染或非法概率。

## 9. 成本、停止条件与尚未冻结项

设 N 为窗口数，M 为合并问题数，E 为新合并区间数，P 为双向比较的候选对数，则三层选择题数量为：

`Q = 5N + M + 5E + 2P`。

这里统计的是问题级推理，批处理多少题不改变总题数。G0 通用评分对照另加 N 题。视频前缀建立、每题 token、缓存峰值和 GPU 生命周期分别计量，不能只按 API 次数估算时间。

按旧窗口数量粗算，TVSum val10 的 1,260 窗口对应 **6,300 个 L1 问题**，全50的 4,213 窗口对应 **21,065 个 L1 问题**，均尚未包含 L2/L3。它们只是规模计算，不是运行申请、预算或耗时预测。若另加五个存在性问题，单窗成本从 5 题变成 5+m 题；是否能靠短题减少计算，只能通过实测回答。
